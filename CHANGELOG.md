# Changelog

All notable changes to Tainer are tracked here. Used as the source for release notes.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow [Semantic Versioning](https://semver.org/) once we cut tagged releases.

Sections per release:

- **Added** — new features
- **Changed** — changes to existing behaviour
- **Fixed** — bug fixes
- **Removed** — features that have been taken out
- **Security** — vulnerability fixes (call these out, even small)

## [Unreleased]

### Added

- **Load balancer: dry-run mode.** Auto-migration now records every move it *would* make as a "dry-run" entry in the activity log — same decision pipeline, same pacing, nothing touched — so you can audit the balancer's judgement for a few days before letting it act. On by default when auto-migration is enabled; turn it off in the settings form once the recommendations look right.
- **Load balancer: containers are protected from surprise downtime.** Proxmox can't live-migrate LXC containers — every automatic move is a restart migration (stop → transfer → start) with real downtime. Containers are now excluded from automatic balancing by default, with an explicit opt-in: allow them always, or only inside downtime windows you define (e.g. `22:00-06:00`, server time, midnight wrap supported). VMs continue to live-migrate freely.
- **Load balancer: maintenance mode (node drain).** Add a node to the new Maintenance Nodes list and the balancer evacuates its guests one at a time to healthy nodes (capacity-checked, ~1/minute), stops placing new deployments on it, and never picks it as a migration target. Guests it can't move (pinned/excluded) raise a drain-warning event so you can move them manually.
- **Load balancer: per-guest control with ProxLB-compatible Proxmox tags.** Tag a guest `plb_ignore` (never migrate), `plb_pin_<node>` (keep on that node), `plb_affinity_<group>` (keep group members together — the balancer won't split them), or `plb_anti_affinity_<group>` (keep members on different nodes — targets already hosting one are rejected). Excluded Nodes / Excluded VMIDs are also now editable in the settings form instead of API-only.
- **Load balancer: concurrency cap.** A new Max Concurrent Migrations setting (default 1) bounds cluster-wide in-flight migrations — including ones still running from previous ticks, which the balancer now tracks to completion via the Proxmox task API — so a hot cluster can't kick off a migration storm.
- **Deploy forms now use live load-balancer scores for the "Automatic" node choice.** When the balancer is enabled, template launches, the VM creator, and base-image deploys pick the suggested node from real-time composite scores (including contention penalties, exclusions, and maintenance state) instead of a static free-memory heuristic. Manual node choice is unchanged.
- **Load balancer: PSI pressure scoring (Proxmox VE 9+).** Node scores now include kernel Pressure Stall Information: when tasks are actually stalling on CPU, memory, or IO (10-second stall average above the threshold, default 10%), the node collects a penalty per pressured resource — catching contention that plain utilization hides (a node at 60% CPU can still be stalling badly). Tunable penalty and threshold in the settings form; nodes on PVE 8 simply don't report PSI and are unaffected.
- **Load balancer: ballooning-aware memory accounting.** For VMs with a balloon driver, migration decisions now use the guest's real memory usage instead of the host-reported figure (which counts the full ballooned allocation and can be several times larger) — so the balancer no longer picks the wrong guest to move or overestimates what a target node needs to hold.
- **Load balancer: cost-benefit migration selection.** Instead of always moving the heaviest guest, the balancer computes how much load an overloaded node actually needs to shed and moves the smallest guest that gets it there — and it always tries VMs (live migration, no downtime) before containers. A new Min Improvement % setting (default 20%) is the explicit floor a target must beat the source by, replacing the previously hardcoded value.
- **Load balancer: predictive balancing (opt-in).** The balancer keeps ~1 hour of score history per node and fits a trend over the last 30 minutes; when a node is confidently forecast (R² above your floor, default 70%) to cross the migration threshold within the horizon (default 30 min), it moves a workload *before* the overload materialises. Every normal safety gate still applies — cooldowns, concurrency cap, container policy, dry-run — and each predictive event logs its full evidence: projected score, trend slope, confidence, and sample count. Off by default.
- **Load balancer: whole-cluster rebalance plans.** A new panel on the load-balancer page computes an optimal multi-move plan — the fewest migrations that most even out the cluster (minimizing the same imbalance measure Proxmox's dynamic CRS uses), honouring capacity headroom, affinity/anti-affinity, pins, exclusions, and maintenance nodes. The plan is a preview: a table of moves with projected imbalance before/after; nothing migrates until you click Apply. Applied plans execute one move at a time under the concurrency cap, each re-validated against live cluster state right before it fires (stale moves are skipped with a logged reason, never forced), survive Tainer restarts mid-plan, and can be cancelled at any time. Containers are only included when explicitly ticked for that plan.
- **Load balancer: per-guest `plb_manual` tag.** Tag a guest `plb_manual` in Proxmox and it's exempt from all *automatic* moves (overload and predictive) but still participates in explicit admin actions — maintenance drains and applied rebalance plans. The per-guest equivalent of VMware DRS's "manual" automation level, alongside the existing `plb_ignore` (never moved by anything).
- **Load balancer: fuller activity log and an in-page explainer.** Circuit-breaker openings/closings, balancer tick errors (rate-limited), settings changes (who changed what), dry-run recommendations, and drain warnings are now all persisted to the activity log alongside migrations. The load-balancer page also gained a "How it works" section, and there's a full write-up in `docs/load-balancer.md`.
- **Tainy can run on your own model.** Admins can point the copilot at any OpenAI-compatible endpoint — vLLM, Ollama, LM Studio, or a corporate LLM gateway — with a custom base URL and model id in Settings → Tainy, instead of DeepInfra. Made for air-gapped and data-locality-conscious deployments: prompts and cluster data never leave your network. https is required (set `TAINER_COPILOT_ALLOW_INSECURE_ENDPOINT=true` to permit plain http on a trusted LAN), and the API key is optional for endpoints that don't need one. Leave the endpoint empty and everything works as before.
- **Per-group copilot tool policy** (Settings → Tainy, admin-only). Restrict what classes of tools each user group can use through the copilot: uncheck "write & admin" and/or "destructive" per group and those tools are both hidden from the model and blocked server-side (re-checked at approval time too). Read tools — lists, metrics, diagnostics — are always available, and every regular permission check still applies on top. Use it for "the helpdesk group can look but not touch" or "operators can start/stop but never delete via AI".
- **Copilot usage by user.** The Tainy settings page now shows admins a per-user spend table — tokens and tool calls today and over the rolling 30-day window — so "who is using the AI, and how much?" has an answer without grepping the audit log.
- **Operator notes for Tainy** (Settings → Tainy, admin-only). Free-text site guidance injected into the copilot's instructions — things like "never restart CT 105 during business hours" or "prefer the servers IP pool for new containers". Every user's copilot follows them; 4,000-character limit.
- **Copilot cost estimation.** Optionally enter your provider's USD price per million input/output tokens and the usage displays (your own usage bar and the admin per-user table) show an estimated dollar cost alongside raw token counts. Purely informational; leave empty to hide.

### Changed

- **Auto-migration behaviour: existing deployments with auto-migration enabled switch to dry-run recommendations until Dry-Run Mode is explicitly unchecked, and containers stop being auto-migrated until opted in.** Both defaults changed to the safe side because container moves cause downtime (see Added). Review the new settings on the load-balancer page after upgrading.
- **Load balancer default score weights are now memory-primary**: memory 50%, CPU 25%, disk 15%, latency 10% (previously CPU 40%, memory 30%, latency 20%, disk 10%). Memory is the truly finite resource — CPU contention degrades gracefully, memory exhaustion OOM-kills — and Proxmox's own scheduler weights memory 5:1 over CPU for the same reason. Only affects sites that never saved custom weights; saved settings keep their values.

- **Docker image library path is now configurable in Settings** (Settings → Docker image library, admin / `manage-settings`), instead of being locked to the `DOCKER_LIBRARY_PATH` environment variable. Set it once in the UI — no redeploy — and the suggested `/app/data/docker-library` lives on the already-mounted data volume, so image pulls work out of the box (the directory is created on the first pull). The env var still works as a fallback when the setting is blank; the setting takes precedence. This unblocks `pull_docker_image` (and the Docker Hub image browser) on deployments that never set the env var.
- **Copilot can deploy a Docker image end-to-end — no deployment template needed.** New tools: `search_docker_images` finds the right Docker Hub namespace (Pi-hole is `pihole/pihole`, not an official image — the assistant now checks instead of guessing); `pull_docker_image` pulls the image into a Proxmox storage as a CT template using Proxmox's native OCI registry pull (the image is validated against Docker Hub first, so a wrong name fails immediately with a helpful message instead of a silent task failure); and `create_container_from_image` creates and starts an LXC from the pulled template — next free VMID, generated root password, the image's default env vars applied automatically (plus any overrides you asked for), DHCP or a static IP from a pool. So "run pihole on node 1" works as search → pull → create, each gated by the usual approval + audit.
- **Copilot can stock ISOs and create VMs from them.** `download_iso` fetches an installer ISO from a URL into a Proxmox storage (SSRF-guarded, and restricted to `TAINER_DOWNLOAD_URL_ALLOWLIST` hosts when that env var is set — and the assistant is instructed to only use a URL you explicitly gave it, never one from a web page or another tool); `create_vm_from_iso` creates a QEMU VM that boots an existing ISO (allocates the VMID, attaches a disk + virtio NIC, mounts the ISO as CD-ROM, leaves it stopped for the installer).

- **Real-time updates.** The dashboard, deployments list, and deployment pages now subscribe to a live event stream: when any guest or node changes state — started from the Proxmox UI, stopped by a colleague, migrated, created, deleted — the page updates within a few seconds instead of waiting for the next poll. Tainer runs one shared watcher per site regardless of how many browsers are connected, and stops watching entirely when nobody is looking. The old periodic refresh remains as a safety net.
- **API tokens for automation** (Settings → API tokens, admin-only). Scoped bearer tokens let scripts, Terraform, or CI call Tainer's API without a browser session: `curl -H "Authorization: Bearer tnr_…"`. Each token gets an explicit permission set and site scope, acts as an operator (admin surfaces and user/group/site management are never token-accessible), supports optional expiry, and shows its last-used time. Tokens are displayed exactly once and stored only as hashes; creation and revocation are audited.
- **Per-deployment firewall panel.** The deployment page now shows the guest-level Proxmox firewall: enabled state with default policies, the rule list, one-click enable/disable, add rule (direction, action, protocol, port, source, comment) and delete — gated on the "Manage security" permission and recorded in the deployment's activity log. The panel reminds you that rules only bite on NICs whose firewall flag is on (toggle per NIC under Network → Switching).
- **Tainer can now back itself up** (Settings → Tainer state backup, admin-only). Tainer's own data — users, sessions, 2FA secrets, encrypted site credentials, audit log, IP pools, policies — is archived as a single passphrase-encrypted file (AES-256-GCM, scrypt key derivation), on a daily schedule and/or on demand, with configurable retention and destination directory. Backups can be downloaded from the UI for off-host copies, and restored on any machine with `scripts/restore-state-backup.mjs` using only the passphrase — no access to the original host required. The Docker image library and previous backups are excluded to keep archives small. Settings changes and manual backups are recorded in the audit log.
- **Virtual switching view (Network → Switching).** Each Proxmox node is rendered as a switch front panel: every Linux bridge is a section, every container/VM network interface is a port chip (green = running, dimmed = stopped, red = link forced down, with VLAN tag and firewall indicators), and the bridge's physical NICs appear as uplink ports. Clicking a port opens its details — and with the "Manage deployments" permission you can disconnect/reconnect the link, change the VLAN tag, set a rate limit, or toggle the Proxmox firewall flag, applied live to the running guest. Changes are recorded in the deployment's activity log.

- **The assistant can now check Proxmox task progress.** A new `get_task_status` tool lets Tainy wait for long-running tasks (image pulls, ISO downloads, backups) and only proceed once they finish — so "pull pihole and deploy it" no longer races the pull.
- **Virtual switching got an operating table.** Below the switch panels there's now a flat, searchable table of every guest interface (name, node, bridge, VLAN, IP, MAC, rate, link state). With the "Manage deployments" permission you can select multiple interfaces and retag or clear their VLAN in one go — each change still individually applied and logged.

### Changed

- **The assistant is now called Tainy.** Renamed everywhere it appears — sidebar, launcher button, settings page, and audit/activity log messages.
- **Tainy streams its replies word-by-word** instead of posting each response as one block, so answers start appearing immediately. Reasoning-model thinking streams into the collapsed "Thought process" section as it happens.
- **Tainy's tool steps stay collapsed by default** — long multi-step answers no longer unfold every result card automatically. Click a step to expand it; approval cards still open on their own.
- **Status badges flip instantly after start/stop.** The status pill on the deployments list and the badge on the container page now change the moment a lifecycle task completes, in the same instant as the action buttons, instead of trailing by a few seconds.
- **Copilot shows its reasoning as a collapsible "Thought process" block.** Reasoning-model output (`<think>…</think>` traces) used to leak into replies as raw text with the tags visible; it's now separated out server-side, rendered collapsed and dimmed above the answer, and never fed back to the model (saves tokens).
- The deployments list and site dashboard now auto-refresh (every 15s and 30s respectively) while the tab is visible, so status changes made outside the app — or lagging behind an action — show up without a manual browser reload.

### Fixed

- **The app container can write Next.js's runtime cache again.** The hardened image made all of `/app` read-only for the app user — including `.next/cache`, which Next needs for data caching and the image optimizer. Every request logged an `EACCES` unhandled rejection and server-side caching silently degraded. The cache directory is now writable (it holds cache artifacts only, so the read-only-code posture is unchanged).
- **Start/stop/restart buttons now show their pending spinner and the page updates when the action completes.** The shared form wrapper was silently discarding submit handlers passed by its callers, so the lifecycle buttons never entered their pending state and never triggered their completion refresh — on the deployments list *and* the deployment detail page. The same bug ate pending-state handlers in the backup/alert policy editors, IP pool settings, node-config snapshots, and identity-provider forms. The buttons also flip to the new state instantly when the task finishes (stop → shows Start, start → shows Stop) instead of waiting for the page re-render, and the deployment detail page auto-refreshes every 15s so status, uptime, and metrics stay live.
- **Stopping (or starting/restarting) a deployment from the server list no longer leaves the row stuck on the old status until a manual browser refresh.** Two causes: the action button's spinner cleared before the Proxmox task had even been registered for tracking, firing its page refreshes too early; and the post-completion refresh happened only once, 1.5s after the task ended — before Proxmox's status endpoint (which updates on a ~10s cadence) reflected the new state. The task tracker now waits for actual completion and refreshes on a staggered schedule until the status settles.
- **Copilot's "Thinking…" indicator no longer disappears mid-turn.** It previously only showed before the first output, so during multi-step tool turns (answer → tools → more work) the chat looked stalled or finished while the model was still working. The indicator now shows whenever the copilot is waiting on the model, and hides only while a tool call's own progress spinner is visible.

### Security

- **Copilot burst rate limit.** The daily token/tool-call budgets bounded total spend but not speed — a user (or a stolen session) could burn the whole day's budget against the site API key in seconds. Copilot messages are now capped at 10 per user per minute on top of the daily budgets; hitting the limit is recorded in the admin audit log.
- **Copilot prompt-injection hardening for external content.** Docker Hub search results contain publicly-authored text (image descriptions) that a hostile publisher could craft to look like instructions to the model. Those results are now fenced as untrusted data with the copilot explicitly instructed to never treat fenced content — or container names/descriptions in any tool result — as instructions. Additionally, when external content has entered a conversation, every subsequent approval card carries a provenance warning so you double-check the proposed action is the one you actually asked for. The existing backstop is unchanged: nothing state-changing executes without your explicit approval.

## [1.5.0] - 2026-07-09

### Added

- **Configurable agent ingest URL.** The LLDP/SNMP setup snippet previously hard-baked Tainer's public origin (`APP_URL`) as the address agents POST to — which fails on LAN deployments where Proxmox nodes can't resolve that hostname (the agent dies with `curl: (6) Could not resolve host`). There's now a per-site **Agent ingest URL** override in Network → Integrations (admin / `manage-security`), plus a global `TAINER_AGENT_BASE_URL` env var. Precedence: per-site override → env var → request origin. The panel shows the effective URL currently baked into new snippets and its source. Validated as a bare origin (scheme + host + optional port, no path). Changing it only affects newly generated snippets; existing nodes keep their value until a token is re-issued or `/etc/tainer-lldp.env` is edited.
- **SNMP polling for the full switch front panel.** LLDP only ever shows the one port a Proxmox node plugs into — a 48-port switch rendered as a lonely single chip. Now, when an admin sets a per-site SNMP community string in **Network → Integrations**, each node's agent also polls every LLDP-discovered neighbour's management IP via SNMPv2c (`IF-MIB` walk: `ifDescr`, `ifAlias`, `ifOperStatus`, `ifAdminStatus`, `ifSpeed`/`ifHighSpeed`, `ifType`, `ifMtu`) on a configurable timer (default 5 min) and POSTs the inventory to a new `/api/internal/snmp-ingest` endpoint. The device detail page then renders the **real chassis** — every physical port with true up/down/admin-disabled state, port names, operator aliases, and link speed, in a UniFi-style front panel with per-port LEDs; LLDP-observed ports get a sky-blue ring so you can see at a glance where your nodes terminate. Falls back to the LLDP-inferred mock when SNMP isn't configured. The community string is stored AES-256-GCM-encrypted under `AUTH_SECRET` (same as 2FA/OIDC secrets), never echoed back to the UI, and only baked into the agent setup snippet at token-issuance time. Same trust model as LLDP — the agent reaches *out*; Tainer never connects in. The extended setup snippet installs `snmp`+`jq`, ships a `tainer-snmp-poll.sh` script, and wires a `tainer-snmp.timer`; it no-ops cleanly until a community string is set, so you can enable SNMP later without re-running it on every node.
- **Tainer Copilot — an embedded AI assistant for diagnosing and managing your cluster** (sidebar slides out from the right, `Cmd/Ctrl+J` to toggle; new "Copilot" entry in the main nav). Ask questions like "what's running on prod?", "which container is using the most memory?", or "restart container 101"; the assistant calls a curated catalog of Tainer/Proxmox tools (list_sites, list_containers, get_container, list_storage_pools, start/stop/restart/shutdown_deployment, update_deployment_resources, destroy_deployment, get_audit_log, etc.) to answer or act. It also understands the site's **IP pools**: ask "give web01 a free IP from the server pool" and it reads pool availability (Tainer + external IPAM merged), picks a specific free address, and proposes a `change_deployment_ip` — the approval card shows the exact address, and the server re-validates availability at execution time so a stale or hallucinated address is refused. New containers can be launched with a **static IP from a pool** too ("deploy grafana with a static IP from the server pool") — the create tool takes an IP pool and assigns the first free address (or one you name) instead of DHCP. It can **delete many at once** too: "delete ignition-02 through ignition-10" is a single `destroy_batch_deployments` call — one confirmation for the whole set, and running guests are hard-stopped first automatically (in parallel, with a bounded wait so a stuck stop can't hang the turn) instead of the old one-at-a-time stop-then-delete dance that stalled on slow models. And it can **create many at once**: "create 10 from the grafana template with static IPs from the server pool" plans all ten hostnames and addresses, shows the full hostname→IP table on a single approval card, and creates the whole batch after **one** confirmation (each container gets its own one-time root password). The first N free pool addresses are reserved in order; if the pool doesn't have enough, it says so rather than half-creating. The copilot's tool catalog also grew a **Backups** group (list all/per-deployment, create a no-downtime backup, restore over a stopped guest with a typed-name confirm), **historical metrics** (`get_deployment_metrics` — CPU/memory/network avg + peak trend over hour→year, rendered as sparklines), **node migration** (move an LXC/VM to another node), and **tag management** (list a site's tags with member counts, add/remove tags on a guest). It also gained **triage & security tools**: `run_diagnostics` (site health scan — offline nodes, full storage, guests missing backups), `get_cve_report` / `run_cve_scan` (vulnerability scan results and fresh scans), `get_alerts` (a site's active alerts) and `get_heartbeat_status` (cluster reachability), plus `get_network_path` — trace a container's physical path (bridge → NIC → upstream switch + port + VLAN) straight from LLDP, so "what switch is web01 behind?" is one question. Rounding it out: **firewall** management (list cluster rules, add a rule, delete by position with a typed confirm), **VM template** listing (creation stays in the UI where ISO/cloud-init choices live), and a set of **admin/config reads** — backup & alert policies, node config snapshots (plus capture-a-snapshot), the ISO library, and read-only user/group listings ("who doesn't have 2FA?", "which group grants admin?"). Deliberately kept out of the copilot: node-config *restore*, user/group *mutations*, and any shell/outbound action — those stay UI-driven to preserve the assistant's no-exfiltration, least-privilege boundary. All go through the same permission/approval model as the rest. And it can **navigate for you**: "take me to that container" opens the deployment's detail page directly (internal app paths only — the assistant cannot send your browser to external URLs). The sidebar is **page-aware**: on a deployment detail page a context chip (e.g. "CT 101 · pve1") shows that "this container" questions resolve to that deployment — click it to detach the context and ask about anything else. **Conversations persist**: every chat auto-saves after each reply (per-user, newest 20 kept, approval tokens stripped) and the history panel in the sidebar header reopens or deletes previous chats — tool cards and all. **Permissions are inherited from your Tainer session** — every tool call goes through the same `requireSession` / `requirePermission` / `requireSiteAccess` / per-site checks the UI uses, so the copilot can never see or do anything you can't. Read tools (list, get, metrics) auto-run; write tools (lifecycle, resource updates) require a one-click approval card in the sidebar with a diff-style summary; destructive tools (delete) additionally require typing the deployment name to confirm. Approval is enforced by a server-issued AES-256-GCM-encrypted token (5-minute TTL, bound to the user's id) — the model can plan whatever it wants, but nothing executes without a fresh token from the approve button. A single **site-wide** DeepInfra API key managed by admins (encrypted at rest with `AUTH_SECRET`, never bundled), choice of Gemma 4 26B A4B (Fast) or Gemma 4 31B (Smart) served through DeepInfra's OpenAI-compatible API, and admin-configurable per-user daily token + tool-call budgets at `/settings/copilot`. Every approved, denied, executed, or failed tool call is written to the admin audit log (new actions: `copilot-tool-approved`, `copilot-tool-denied`, `copilot-tool-executed`, `copilot-tool-failed`, `copilot-budget-exceeded`, `copilot-settings-updated`). Action surface is strictly Tainer-internal — no outbound HTTP, no email/Slack, no arbitrary shell — closing the prompt-injection exfiltration vector if a tool response ever contains hostile text. Hard per-turn ceilings (15 tool calls, 4 096 output tokens) plus admin-configurable per-user daily caps prevent runaway loops from draining the site key.
- **LLDP topology discovery per site** (`/sites/<slug>/network`). Each Proxmox node runs a tiny push agent (a systemd timer + 8-line shell script — `apt install lldpd` plus a 60-second loop that POSTs `lldpcli show neighbors -f json0` to Tainer) and Tainer aggregates the snapshots into a topology view. Three tabs: a hierarchical SVG **Topology** (upstream switches/routers on top, Proxmox agents on the bottom, edges labelled with VLAN when advertised), a **Devices** table that lists every discovered neighbour with capabilities/management-IP/last-seen, and an **Integrations** panel where the operator issues per-node bearer tokens and copies the setup snippet. Clicking a device opens a detail page with a **UniFi-style front-panel mock** — port chips coloured for active / stale / unknown state, with the chassis size inferred from the highest LLDP-observed port number (rounded up to 8/16/24/28/32/48/52) and SFP/uplink ports broken out to the side. Clicking a chip expands an inline detail panel showing the port description, VLAN, last-seen age, and which Proxmox node + local interface terminates at it. Trust direction is inbound only: the agent reaches *out* to Tainer; Tainer never reaches into the nodes. That means hosted-Tainer deployments where the Proxmox network refuses inbound SSH work out of the box. Tokens are stored as SHA-256 hashes (plaintext shown exactly once at issuance), bound to the issuing site, individually revocable, and per-token rate-limited at the ingest endpoint. Every issuance, revocation, snapshot wipe, and revoked-token reuse attempt is written to the admin audit log (new actions: `lldp-token-issued`, `lldp-token-revoked`, `lldp-snapshots-cleared`, `lldp-ingest-rejected`). Permission gate: per-site `manage-security` for token operations; per-site access for viewing.
- **"Network path" card on every deployment detail page.** Shows the full chain `container netN → bridge → uplink NIC → upstream switch + port + VLAN` for each network interface, resolved by combining the Proxmox container/VM config with the host's bridge configuration and the latest LLDP snapshot from that node's agent. Each hop links through: clicking the upstream switch lands on its front-panel page so the operator can see what else is on the same switch. When no LLDP agent has posted from the hosting node, the card surfaces only the local chain (container → bridge → NIC) with a clear "no LLDP neighbour observed" marker — the failure mode is honest rather than empty. The card hides itself entirely when the deployment has no `netN` interfaces.
- **LLDP polish: live refresh, port pulse, device annotations, and link-flap history.** Topology and device pages now refresh themselves every 60 seconds (aligned with the agent push cadence, paused while the tab is hidden, no thrash). Ports observed in the most recent push subtly pulse on the front panel — a "this link is actually alive right now" cue that goes quiet for stale ports. Every discovered device can be annotated with a friendly name (overrides the LLDP-advertised `systemName` in listings and the detail header), a manual port-count override (replaces the inferred chassis size on the front panel — useful when LLDP-observed ports don't span the real chassis), and a free-text notes field; the form sits on the device detail page and is gated by per-site `manage-security`. Annotation mutations are audited (`lldp-annotation-updated`, `lldp-annotation-removed`). Finally, the ingest endpoint now diffs each new snapshot against the previous one from the same agent and emits per-port `link-up` / `link-down` events to a new capped log (`lldp-events.json`, max 10 000 entries), surfaced as a "Link history" card on the device detail page so operators can spot flapping. First-push events are suppressed (no fake `link-up` storm when an agent comes online).
- **Update-available badge in the sidebar.** The running version is now baked into the production image at build time (`TAINER_VERSION`, set by `scripts/publish-docker.sh` from the release tag) and compared hourly against the highest `vX.Y.Z` tag on Docker Hub (`tainersh/tainer`). When a newer version is published, a small green `→ vX.Y.Z` indicator appears next to the version line in the sidebar — operators still pull and redeploy themselves; Tainer never updates itself from inside its own container. The check is unauthenticated, cached in memory (1h on success, 5m on failure), and skipped entirely for local dev builds. Set `TAINER_DISABLE_UPDATE_CHECK=true` to suppress the outbound call in air-gapped deployments.
- **LDAP / Active Directory authentication on the standard sign-in form.** Configure the directory once at `/ldap` (admin only) and the existing email + password form transparently authenticates against the directory after local-password lookup fails — no separate "Sign in with LDAP" button. Search-then-bind pattern: a service-account binds, searches for the user with an RFC-4515-escaped filter, and the user's password is verified by re-binding as their DN. LDAPS is required by default (plaintext refused unless `TAINER_LDAP_ALLOW_INSECURE=true`); TLS certificate validation is strict by default (`TAINER_LDAP_INSECURE_TLS=true` to opt out, with a loud warning every connection). The bind password is encrypted at rest with the same AES-256-GCM helpers that protect 2FA and OIDC secrets. Auto-provisioning is opt-in and requires a non-empty allowed-domain list when the default role is admin (same foot-gun guard as OIDC). ### Fixed

- **IP pool subnet parsing was broken for any network with first octet ≥ 128.** A 32-bit signed-int overflow in `parseSubnet()`: `addressInt & mask` returns a signed integer, so for `192.168.x`, `172.16.x`, or any public range the computed `networkInt`/`firstHostInt`/`lastHostInt` flipped negative. Range comparisons in `validateGateway` then rejected legitimate gateways like `192.168.100.1` for `192.168.100.0/24` with "Gateway must fall within the selected subnet's usable host range" — even though it is. The string outputs were correct (`intToIpv4` uses `>>>` which is unsigned), masking the bug for years. `10.x.x.x` happens to have the high bit clear so worked fine. Added explicit `>>> 0` coercion to `networkInt` and `broadcastInt` to keep them in unsigned space throughout.
- **Server actions that did `return withSiteConfig(...)` (no `await`) bypassed their own try/catch when the inner work threw.** In an async function, `return rejectedPromise` propagates the rejection to the awaiter without triggering the surrounding `catch` — so when a form submission threw (e.g. invalid IP pool gateway, bad subnet, malformed input), the rejection escaped the action and Next.js surfaced "Application error: a server-side exception has occurred" instead of the intended error toast. 61 call sites across 18 `*-actions.ts` files were patched to `return await withSiteConfig(...)`. ### Security

- **Rate-limit bypass via `X-Forwarded-For` header (RL-1).** The login and password-reset rate limits keyed on `email:ip`, where the `ip` was read straight from the `X-Forwarded-For` request header. A direct caller could rotate the header per request to mint a fresh bucket and effectively defeat per-IP lockout. `X-Forwarded-For` is now ignored unless `TAINER_TRUST_PROXY_HEADERS=true` is set explicitly; the default falls back to per-email rate limiting, which the attacker cannot rotate around.
- **Cross-site information disclosure on `/api/proxmox/rrd`, `/api/proxmox/task-status`, `/api/sites/overview`, and `/api/sites/status` (AUTHZ-1).** These routes only checked that the caller had a session, not that they had access to the requested site. Any logged-in operator could pull RRD time-series, poll task UPIDs, and enumerate every enabled site (status, location, deployment count, version banner) — including sites their permissions didn't cover. Each route now enforces `hasSiteAccess` per-request or filters the response to `accessibleSiteIds`.
- **SSO email-match account takeover (SSO-1 / C1).** When an OIDC sign-in didn't match an existing IdP-linked record, `signInWithSso` fell back to matching by email and silently bound the SSO subject to whatever local user owned that address. An attacker who could register a target's email at a permissive IdP could sign in as that local user — including admins. Email-fallback now refuses to adopt accounts that have a local password, 2FA enrolled, or a different SSO link; an admin must explicitly link the provider first. The `email_verified` claim is also enforced — sign-in is refused outright when the IdP reports the email as unverified.
- **2FA bypass via SSO (SSO-2 / C2).** The previous SSO path issued a session for any matched user without checking 2FA, so an SSO-eligible identity at the IdP bypassed local TOTP entirely. Combined with the email-match guard above, users with 2FA enrolled can no longer be adopted by a fresh SSO sign-in — the account stays under local-credential control until an admin links it.
- **OIDC issuer accepted `http://` (OIDC-1 / H1).** Issuer validation accepted any `http://` or `https://` URL, leaving discovery and token exchange MITM-able when an admin pasted a non-HTTPS issuer. `http://` is now rejected unless `TAINER_OIDC_ALLOW_INSECURE_ISSUER=true` is set explicitly for local development.
- **Auto-provisioning admins with no domain restriction (CFG-1 / M1).** The IdP-provider validator allowed `autoProvision: true` together with `defaultRole: admin` and an empty `allowedEmailDomains` — a foot-gun that turned anyone who could sign in at the IdP into a Tainer admin. The validator now refuses that combination and asks for an explicit allow-list.
- **Email-domain allowlist misclassified multi-`@` addresses (M5).** `isEmailAllowed` used `split("@")[1]`, so an address like `attacker@evil.example@trusted.example` matched as `evil.example` and could pass an allowlist that only named `trusted.example`. The check now uses the substring after the *last* `@`, matching canonical mailbox parsing.
- **Password-reset links no longer persisted to disk (DBG-1).** When SMTP was unconfigured, password-reset URLs (containing the single-use reset token in the path) were written to `password-reset-debug.json` in the data directory and kept for the last 25 attempts. Any disk-level read — backup leak, snapshot copy, post-RCE — let an attacker hijack pending resets. The link is now logged to stderr only; the operator running the container reads it from container logs and it disappears with the line.
- **Cluster credentials no longer logged on every RRD request.** The `/api/proxmox/rrd` handler logged the active site's `apiUrl` and `username` per request, exposing them to anyone with read access to container logs. Both log lines were removed.
- **Source maps no longer ship in the production Docker image (F1/F10).** The Dockerfile previously deleted `*.map` files in a `RUN` step *after* the `COPY --from=builder /app/.next` — but Docker layers are append-only, so the original bytes still lived in the COPY layer and were extractable from any pulled image via `docker save | tar -x`. Cleanup is now done in the same `RUN` as `npm run build` in the builder stage, so the runtime stage never sees source maps in its history. (Existing published images should be re-pulled / re-built to benefit; the old layers remain on Docker Hub.)
- **`AUTH_SECRET` is now mandatory in production (F6).** The auth secret is the crypto root for session cookies, mobile JWTs, 2FA secrets, and Proxmox credential encryption. Tainer used to auto-generate one to `auth-secret.txt` in the data directory if `AUTH_SECRET` was unset — convenient, but it meant any disk-level read (backup, snapshot, post-RCE) handed an attacker the ability to mint admin sessions and decrypt every Proxmox password. When `NODE_ENV=production` the app now refuses to start without `AUTH_SECRET` set as an env var, and the error message tells you to generate one with `openssl rand -base64 32`. The on-disk fallback is still available for development.
- **`manage-groups` privilege escalation to admin (RBAC-1 / C3).** A user with the `manage-groups` permission — intended for shuffling membership of non-privileged groups — could create a new group with `isAdmin: true` and assign themselves to it. `updateUserGroups` derives `user.role` from group membership, so the assignment flipped the caller to admin and the admin-role short-circuit in `hasPermission` then granted full takeover. Operations that touch admin groups (creating one, flipping `isAdmin` on or off, assigning a user into one) now require admin role explicitly, and self-promotion via the group-assignment endpoint is blocked outright as a defense-in-depth guard.

### Removed

- **The `role === "admin"` short-circuit in capability checks.** Previously `hasPermission(session, p)` returned `true` for any `p` whenever `session.user.role === "admin"` — any code path that flipped role to admin granted everything regardless of what `permissions` actually contained. Admins now have the full permission set populated explicitly in `session.user.permissions` at session-hydration time, and `hasPermission` is strict list-membership. Visible behaviour is unchanged (admins still do everything), but a future regression that mutates role outside the group-management path can no longer escalate. `requireAdminSession` and the binary "is admin?" UI checks (sidebar visibility, page-level admin-only gates) keep using `role` as before — only ad-hoc capability gates were affected.

### Changed (security)

- **Container `/app` is no longer writable by the runtime user (IMG-1).** The Dockerfile now `chown root:tainer /app` with `0750`/`0640` perms; only `/app/data` is writable by `tainer`. A future code-exec-in-container bug can no longer rewrite `server.mjs`, `node_modules/`, or `.next/server/*.js` for persistence across restarts.
