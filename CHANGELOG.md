# Changelog

All notable changes to Tainer are tracked here. Used as the source for release notes.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow [Semantic Versioning](https://semver.org/) once we cut tagged releases.

Sections per release:

- **Added** — new features
- **Changed** — changes to existing behaviour
- **Fixed** — bug fixes
- **Removed** — features that have been taken out
- **Security** — vulnerability fixes (call these out, even small)

## [Unreleased]

### Upgrade notes

- **Set AUTH_SECRET before you upgrade.** Production still refuses to run without it and now checks at boot. The stock `docker-compose.yml` and the README examples will not start until it is set (for example in `.env`). Generate one with `openssl rand -base64 32` and keep it the same across upgrades.
- **Password reset no longer turns off 2FA.** A user who lost both their authenticator and their recovery codes needs an admin to clear 2FA with the new Reset 2FA button on the Users page.
- **Providers that leave out email_verified need a checkbox.** For Microsoft Entra ID and similar providers, linked users still sign in, but matching an existing account by email and auto-creating accounts are refused until you enable "Trust email without email_verified claim" on the provider. The same setting is needed to use preferred_username or upn as the email.
- **Behind a reverse proxy, set APP_URL or TAINER_TRUST_PROXY_HEADERS=true.** SSO no longer trusts X-Forwarded-Proto/Host by default. Without one of these the redirect URI falls back to the request URL and your identity provider may reject it.
- **Editing a site's connection needs the Proxmox password.** Changing the API URL, username, TLS mode or custom CA fails unless you type the password again in the same save.
- **API tokens are limited to their site scope.** Tokens no longer pass global permission checks, so scripts that used one for node config, updates, backup policies, ISO downloads, Storage Box, SSH authority, heartbeat, or deployment delete, migrate and recreate are refused. The /api routes keep working with per-site grants.
- **Manage users and Manage groups cannot grant more than the holder has.** Only admins can create admins, reset an admin's password or clear an admin's lockout. Group managers can only hand out permissions and sites they hold, and cannot change their own groups or an admin's. Groups only take Manage users, Manage sites and Manage groups as global permissions; site permissions saved in a group's global list are ignored, so grant them per site.
- **Strict SSH host key policy is enforced everywhere.** The CVE scanner and the debsecan install after container create no longer fall back to accept-new, so sites set to strict need a `known_hosts` file.
- **AIA certificates only chain to trusted roots.** If your Proxmox server's issuing CA is not a system root, paste it into the site's custom CA field.
- **Webhooks do not follow redirects.** A 3xx response now counts as a failed delivery, so point webhooks at the final URL.
- **The Docker image runs on Node 24.** Nothing to do unless you build your own image or pin the base image. The overview map now needs a browser with WebGL2.

### Added

- **Load balancer: dry-run mode.** Auto-migration can record every move it *would* make as a "dry-run" entry in the activity log, using the same decision pipeline and pacing without touching anything, so you can check the balancer's choices for a few days before letting it act. On by default when auto-migration is enabled; turn it off in the settings form once the recommendations look right.
- **Load balancer: containers are protected from surprise downtime.** Proxmox can't live-migrate LXC containers, so every automatic move is a restart migration (stop → transfer → start) with real downtime. Containers are now left out of automatic balancing by default. You can allow them always, or only inside downtime windows you define (e.g. `22:00-06:00`, server time, windows past midnight work). VMs still live-migrate freely.
- **Load balancer: maintenance mode (node drain).** Add a node to the new Maintenance Nodes list and the balancer moves its guests off one at a time to healthy nodes (capacity-checked, about one a minute), stops placing new deployments on it and never picks it as a migration target. Guests it can't move (pinned or excluded) raise a drain warning so you can move them by hand.
- **Load balancer: per-guest control with ProxLB-compatible Proxmox tags.** Tag a guest `plb_ignore` (never migrate), `plb_pin_<node>` (keep on that node), `plb_affinity_<group>` (keep group members together) or `plb_anti_affinity_<group>` (keep members on different nodes; targets already hosting one are rejected). Excluded Nodes and Excluded VMIDs can now be edited in the settings form instead of only through the API.
- **Load balancer: concurrency cap.** A new Max Concurrent Migrations setting (default 1) limits in-flight migrations across the cluster, including ones still running from earlier ticks, which the balancer now tracks to completion through the Proxmox task API. A hot cluster can no longer start a migration storm.
- **Deploy forms use live load-balancer scores for the "Automatic" node choice.** With the balancer enabled, template launches, the VM creator and base-image deploys pick the suggested node from real-time scores (including contention penalties, exclusions and maintenance state) instead of a static free-memory guess. Manual node choice is unchanged.
- **Load balancer: PSI pressure scoring (Proxmox VE 9+).** Node scores now include kernel Pressure Stall Information. When tasks are really stalling on CPU, memory or IO (10-second stall average above the threshold, default 10%), the node gets a penalty per pressured resource, which catches contention that plain utilization hides: a node at 60% CPU can still be stalling badly. Penalty and threshold are tunable in the settings form; PVE 8 nodes don't report PSI and are unaffected.
- **Load balancer: ballooning-aware memory accounting.** For VMs with a balloon driver, migration decisions use the guest's real memory usage instead of the host-reported figure, which counts the full ballooned allocation and can be several times larger. The balancer no longer picks the wrong guest to move or overestimates what a target node needs to hold.
- **Load balancer: cost-benefit migration selection.** Instead of always moving the heaviest guest, the balancer works out how much load an overloaded node needs to shed and moves the smallest guest that gets it there, always trying VMs (live migration, no downtime) before containers. A new Min Improvement % setting (default 20%) sets how much better a target must score than the source, replacing the old hardcoded value.
- **Load balancer: predictive balancing (opt-in).** The balancer keeps about an hour of score history per node and fits a trend over the last 30 minutes. When a node is confidently forecast (R² above your floor, default 70%) to cross the migration threshold within the horizon (default 30 min), it moves a workload *before* the overload happens. The usual safety gates still apply (cooldowns, concurrency cap, container policy, dry-run), and each predictive event logs its evidence: projected score, trend slope, confidence and sample count. Off by default.
- **Load balancer: whole-cluster rebalance plans.** A new panel on the load-balancer page computes a multi-move plan: the fewest migrations that most even out the cluster, using the same imbalance measure as Proxmox's dynamic CRS, while honouring capacity headroom, affinity and anti-affinity, pins, exclusions and maintenance nodes. The plan is a preview with projected imbalance before and after, and nothing migrates until you click Apply. Applied plans run one move at a time under the concurrency cap, recheck each move against live cluster state right before it runs (stale moves are skipped with a logged reason, never forced), survive Tainer restarts and can be cancelled at any time. Containers are only included when ticked for that plan.
- **Load balancer: per-guest `plb_manual` tag.** A guest tagged `plb_manual` in Proxmox is exempt from all *automatic* moves (overload and predictive) but still takes part in explicit admin actions: maintenance drains and applied rebalance plans. It is the per-guest version of VMware DRS's "manual" automation level, next to the existing `plb_ignore` (never moved by anything).
- **Load balancer: fuller activity log and an in-page explainer.** Circuit breaker openings and closings, balancer tick errors (rate limited), settings changes (who changed what), dry-run recommendations and drain warnings now go to the activity log alongside migrations. The load-balancer page also has a "How it works" section, and there is a full write-up in `docs/load-balancer.md`.
- **Tainy can run on your own model.** Admins can point Tainy at any OpenAI-compatible endpoint (vLLM, Ollama, LM Studio or a company LLM gateway) with a custom base URL and model id in Settings → Tainy, instead of DeepInfra. Meant for air-gapped setups: prompts and cluster data stay on your network. https is required (set `TAINER_COPILOT_ALLOW_INSECURE_ENDPOINT=true` to allow plain http on a trusted LAN) and the API key is optional. Leave the endpoint empty and nothing changes.
- **Per-group Tainy tool policy** (Settings → Tainy, admins only). Uncheck "write & admin" and/or "destructive" for a user group and those tools are hidden from the model and blocked on the server, checked again at approval time. Read tools (lists, metrics, diagnostics) are always available, and the normal permission checks still apply on top. Use it for "helpdesk can look but not touch" or "operators can start and stop but never delete through Tainy".
- **Tainy usage by user.** The Tainy settings page shows admins a per-user table of tokens and tool calls for today and the rolling 30 days, so you can see who uses it and how much without digging through the audit log.
- **Operator notes for Tainy** (Settings → Tainy, admins only). Free-text site guidance added to Tainy's instructions, like "never restart CT 105 during business hours" or "prefer the servers IP pool for new containers". Every user's Tainy follows them. 4,000 character limit.
- **Tainy cost estimates.** Enter your provider's USD price per million input and output tokens and the usage displays (your own usage bar and the admin per-user table) show an estimated cost next to the token counts. Informational only; leave it empty to hide it.
- **Tainy can deploy a Docker image without a deployment template.** `search_docker_images` finds the right Docker Hub namespace (Pi-hole is `pihole/pihole`, not an official image, so Tainy checks instead of guessing). `pull_docker_image` pulls the image into Proxmox storage as a CT template with Proxmox's native OCI pull, after checking the name against Docker Hub so a wrong name fails right away with a useful message. `create_container_from_image` creates and starts an LXC from that template with the next free VMID, a generated root password, the image's default env vars plus any overrides you asked for, and DHCP or a static IP from a pool. "run pihole on node 1" becomes search, pull, create, each behind the usual approval and audit.
- **Tainy can stock ISOs and create VMs from them.** `download_iso` fetches an installer ISO from a URL into Proxmox storage. It is SSRF-guarded, limited to `TAINER_DOWNLOAD_URL_ALLOWLIST` hosts when that is set, and Tainy only uses a URL you gave it, never one from a web page or another tool. `create_vm_from_iso` creates a QEMU VM that boots an existing ISO with a new VMID, a disk, a virtio NIC and the ISO as CD-ROM, and leaves it stopped for the installer.
- **Tainy can check Proxmox task progress.** A new `get_task_status` tool lets Tainy wait for long tasks (image pulls, ISO downloads, backups) to finish before moving on, so "pull pihole and deploy it" no longer races the pull.
- **Real-time updates.** The dashboard, deployments list and deployment pages subscribe to a live event stream. When a guest or node changes state (started from the Proxmox UI, stopped by a colleague, migrated, created, deleted) the page updates within a few seconds instead of waiting for the next poll. Tainer runs one watcher per site however many browsers are connected, and stops watching when nobody is looking. The old periodic refresh stays as a fallback.
- **API tokens for automation** (Settings → API tokens, admins only). Bearer tokens let scripts, Terraform or CI call Tainer's API without a browser session: `curl -H "Authorization: Bearer tnr_…"`. Each token has its own permission set and site scope, acts as an operator on the sites in that scope, and never reaches admin pages or user, group and site management. Tokens can expire, show their last-used time, are displayed once and are stored only as hashes. Creation and revocation are audited.
- **Per-deployment firewall panel.** The deployment page shows the guest-level Proxmox firewall: enabled state and default policies, the rule list, one-click enable and disable, add rule (direction, action, protocol, port, source, comment) and delete. It needs Manage security on the site, and changes go to the deployment's activity log. Rules only apply on NICs with the firewall flag on (`firewall=1` on the netN line in Proxmox), and the panel says so.
- **Tainer can back itself up** (Settings → Tainer state backup, admins only). Users, sessions, 2FA secrets, encrypted site credentials, the audit log, IP pools and policies go into one passphrase-encrypted file (AES-256-GCM, scrypt key derivation), daily and/or on demand, with configurable retention and destination directory. Backups can be downloaded from the UI for off-host copies and restored on any machine with `scripts/restore-state-backup.mjs` using only the passphrase. The Docker image library and older backups are left out to keep archives small. Settings changes, manual backups and downloads are audited.
- **Admins can reset a user's 2FA.** On the Users page an admin can clear two-factor authentication for a user who lost both their authenticator and their recovery codes. The user is signed out everywhere and the reset is recorded in the audit log. Manage users holders, API tokens and your own account cannot use it.

### Changed

- **Load balancer settings explain themselves inline.** Every setting, score column and rebalance-plan field has a small ⓘ you can hover, focus or tap for a short explanation of what it does and what changing it means. The helper paragraphs it replaced are gone, and "How it works" is now a collapsed six-line summary. The full write-up is still in `docs/load-balancer.md`.
- **Auto-migration starts in dry-run and leaves containers alone until you opt in.** Existing sites with auto-migration enabled get dry-run recommendations until Dry-Run Mode is unchecked, and containers are no longer auto-migrated until allowed. Both defaults moved to the safe side because container moves cause downtime (see Added). Review the new settings on the load-balancer page after upgrading.
- **Load balancer default score weights are now memory first.** Memory 50%, CPU 25%, disk 15%, latency 10% (was CPU 40%, memory 30%, latency 20%, disk 10%). CPU contention degrades gracefully but memory exhaustion OOM-kills, and Proxmox's own scheduler weights memory 5:1 over CPU for the same reason. Only sites that never saved custom weights are affected.
- **Docker image library path is set in Settings.** Settings → Docker image library (admins only) sets it without a redeploy, instead of only through the `DOCKER_LIBRARY_PATH` environment variable. The suggested `/app/data/docker-library` sits on the data volume that is already mounted, so image pulls work out of the box (the directory is created on the first pull). The env var is still used when the setting is blank. This unblocks `pull_docker_image` and the Docker Hub image browser on installs that never set the env var.
- **The assistant is now called Tainy.** Renamed everywhere it appears: sidebar, launcher button, settings page and audit and activity log messages.
- **Tainy streams its replies.** Answers appear word by word instead of as one block, so they start showing right away. Reasoning-model thinking streams into the collapsed "Thought process" section as it happens.
- **Tainy's tool steps stay collapsed.** Long multi-step answers no longer unfold every result card. Click a step to expand it; approval cards still open on their own.
- **Tainy shows its reasoning in a collapsible "Thought process" block.** Reasoning-model output (`<think>…</think>`) used to leak into replies as raw text with the tags visible. It is now split out on the server, shown collapsed and dimmed above the answer, and never sent back to the model, which saves tokens.
- **Status badges flip right after start and stop.** The status pill on the deployments list and the badge on the container page change as soon as a lifecycle task completes, together with the action buttons, instead of a few seconds later.
- **The deployments list and site dashboard refresh themselves.** They reload every 15s and 30s respectively while the tab is visible, so changes made outside Tainer, or that lag behind an action, show up without a browser reload.
- **Site operators can manage their own site.** Users with the matching site permission can now delete, migrate and recreate deployments, manage backup policies, refresh the package index, and open the updates, diagnostics and CVE scanner pages for that site. Before, these were admin only. The delete, recreate, migrate, backup, snapshot and firewall controls on the deployment and backups pages now show for users who hold the matching permission and stay hidden from those who don't.
- **The Docker image runs on Node 24.** Node 20 is end of life, so both build stages use `node:24-alpine`, and dependencies were updated (see Security). The overview map moved to maplibre-gl 6, which needs a browser with WebGL2.

### Fixed

- **Recovery codes work when the 2FA secret cannot be read.** If a user's authenticator secret could not be decrypted, for example after AUTH_SECRET changed, the 2FA step failed with a decryption error and refused valid recovery codes as well. Sign-in, the mobile app and the in-app SSH step-up now accept a recovery code in that case. Authenticator codes stay refused until 2FA is set up again.
- **The app container can write the Next.js runtime cache again.** The hardened image made all of `/app` read-only for the app user, including `.next/cache`, which Next needs for data caching and the image optimizer. Every request logged an `EACCES` unhandled rejection and server-side caching quietly degraded. The cache directory is now writable; it only holds cache files, so the code stays read-only.
- **Start, stop and restart buttons show their spinner and the page updates when the action completes.** The shared form wrapper dropped submit handlers passed by its callers, so the lifecycle buttons on the deployments list and the deployment page never showed a pending state or refreshed on completion. The same bug hit the backup and alert policy editors, IP pool settings, node config snapshots and identity provider forms. The buttons now flip to the new state as soon as the task finishes, and the deployment page refreshes every 15s so status, uptime and metrics stay current.
- **Starting, stopping or restarting from the server list no longer leaves the row on the old status.** The button's spinner cleared before the Proxmox task was registered for tracking, so the refresh fired too early, and the single refresh after completion ran 1.5s after the task ended, before Proxmox's status endpoint (about a 10s cadence) caught up. The task tracker now waits for completion and refreshes on a staggered schedule until the status settles.
- **Tainy's "Thinking…" indicator no longer disappears mid-turn.** It only showed before the first output, so during multi-step tool turns the chat looked stalled or finished while the model was still working. It now shows whenever Tainy is waiting on the model and hides only while a tool call's own progress spinner is visible.
- **A wrong 2FA code keeps the code form.** A mistyped authenticator code no longer sends you back to the email and password form, so SSO users can try again without redoing the provider sign-in.
- **Opening a site you cannot access lands on your first accessible site.** Before, it sometimes went to the overview map instead.
- **Deployment activity and SSH host key entries are no longer lost.** Concurrent writes to these logs are queued instead of overwriting each other.
- **Image env defaults are only saved after a successful pull.** A pull from the UI or Tainy that fails or hits an existing file no longer overwrites an image's default env vars, which could end up describing a different image than the file on disk.
- **Faster recovery from slow certificate servers.** If fetching missing intermediate certificates times out, Tainer tries again after about two minutes instead of an hour.

### Security

- **Site pages check sign-in and site access themselves.** Every page under a site now checks the session and access to that site before loading data. A crafted request that skipped the layouts could read cluster data without signing in, or read another site's data. Page requests without a session cookie are also redirected to /login early.
- **Console access checks the site.** Web and mobile console tickets and the console websocket require access to the guest's site, and unknown or disabled sites no longer fall back to the environment Proxmox credentials.
- **Password reset keeps two-factor authentication.** Resetting a password no longer turns off 2FA, so a reset link alone cannot take over an account. Sign-in after a reset still asks for an authenticator or recovery code.
- **SSO asks for your Tainer 2FA code.** Users with 2FA enrolled must enter their authenticator or recovery code after signing in with an identity provider. The sso-login audit entry is written once the code is accepted and names the provider.
- **SSO needs a verified email to match or create accounts.** Sign-in is refused when the identity provider says email_verified is false. When the claim is missing, users already linked to the provider still sign in, but matching an existing account by email and auto-creating accounts are refused unless the provider has "Trust email without email_verified claim" on. Tainer accepts the claim as a boolean or a string, reads it from the userinfo endpoint when the ID token leaves it out, and the error message names the setting that fixes it.
- **SSO cannot take over LDAP accounts.** Signing in with an identity provider no longer links to an existing LDAP user just because the email matches.
- **SSO redirects cannot be steered.** The return path after sign-in must be a same-origin path, so links with backslashes or tabs cannot send users to another site. The public callback URL comes from APP_URL, or from X-Forwarded-Proto/Host only when TAINER_TRUST_PROXY_HEADERS=true.
- **Non-admins can no longer create or take over admin accounts.** Holding Manage users is no longer enough to create an admin, reset an admin's password or clear an admin's lockout. Non-admins also cannot manage users who have more access than they do, or create users in such groups.
- **Group managers can only grant access they hold.** A non-admin with Manage groups can no longer give a group permissions or sites they lack, edit or delete groups with more access than their own, or change an admin's groups or their own. Groups only accept Manage users, Manage sites and Manage groups as global permissions.
- **API tokens stay on their sites.** A token no longer passes global permission checks, so it cannot run node config, updates, backups, ISO downloads, Storage Box, SSH authority, heartbeat or deployment delete, migrate and recreate on any site. The /api routes still work with per-site grants.
- **Tag, snapshot, template and image pull actions check the site.** Creating, editing and assigning tags and bulk start, stop, restart or shutdown by tag need Manage deployments on that site; before, any signed-in user or API token could run them against any site. Creating snapshots needs Manage snapshots. Creating or deleting templates, upstream template import, Docker Hub sync and registry or Gitea pulls need Manage templates.
- **ISO download, Storage Box, node configs and config snapshots are scoped to the site.** They check the permission on the site itself instead of a global grant. Taking, restoring or deleting config snapshots and managing snapshot policies also need access to that site.
- **Read endpoints check site access.** The command palette and the load balancer config and status endpoints refuse callers with no access to the site, and only admins can query task status without a site.
- **Deleting a deployment needs the delete permission.** Deleting a container or VM from the UI needs Delete deployments on the site, the same as Tainy. Recreating from a template removes the old guest and its volumes, so it needs both Manage deployments and Delete deployments.
- **Changing a site's connection needs the password.** Editing the API URL, username, TLS mode or custom CA needs the Proxmox password in the same save, so the stored password cannot be sent to a new endpoint. The change also drops the cached Proxmox login everywhere, console sessions included, so an old ticket never goes to a new address.
- **Saved secrets are not reused for a new endpoint.** Changing an identity provider's issuer URL or client ID, or the LDAP server URL or bind DN, needs the client secret or bind password again, and the audit log records the old and new values. Changing Tainy's custom endpoint URL clears the stored API key.
- **AIA certificates can no longer add trust.** Intermediates fetched from a server's AIA link are only used when they chain to a system root or the site's custom CA, so a self-signed certificate served over AIA is ignored. Certificate auto-detect rejects cross-site requests and follows at most three redirects.
- **SSH follows the site host key policy everywhere.** The debsecan install after container create and the CVE scanner use the site's policy, and strict mode no longer falls back to accepting new keys. SSH usernames starting with `-` are refused.
- **Webhook SSRF guard hardened.** Webhooks no longer follow redirects and are checked against the address actually connected to. IPv4-mapped, NAT64 and 6to4 IPv6 addresses count as private.
- **Backup delete checks the volume ID.** Deleting a backup refuses volume IDs that do not belong to the selected storage or that contain path traversal.
- **AUTH_SECRET is checked at boot.** Production exits at startup with a clear message when AUTH_SECRET is missing, instead of failing later at login. The stock `docker-compose.yml` and the README examples now require it.
- **2FA setup asks for your password.** Turning on two-factor authentication needs your current password, or a sign-in within the last 10 minutes for SSO and LDAP accounts, and signs out your other sessions. SSO and LDAP users can disable 2FA again within 10 minutes of signing in.
- **Login lockout can no longer be used against other users.** Lockout is tied to the email and client address, so someone else cannot lock an admin out. After repeated failures against one account or from one address, each further attempt waits longer, up to a minute, even when requests come from many places. Flooding sign-ins for made-up accounts no longer clears an existing lockout, and IPv6 clients are grouped by their /64.
- **Forgot-password no longer reveals accounts.** The reset form always gives the same answer and response time, and requests are limited per client address.
- **The audit log records more and cannot be flooded.** Failed 2FA codes, password verified while waiting for 2FA, password reset requests and completions, password changes, first admin setup, in-app SSH 2FA checks, state backup downloads and failed SSO sign-ins (sso-login-failure) are now recorded. Repeated failures from unknown callers are throttled and summarized so they cannot push admin events out of the log.
- **Tainy approvals work once.** Each approval carries a unique id and can be used a single time, even if the token is altered and sent again. Approving is refused when Tainy is disabled or the daily tool-call budget is used up. Approval cards show every argument before you approve, with passwords, tokens and keys masked.
- **Tainy no longer keeps generated root passwords.** Passwords for new containers are shown once on the result card, never sent back to the model and never saved in chat history. Passwords already in saved chats are removed the next time chats load.
- **Tainy prompt-injection hardening for external content.** Docker Hub search results contain publicly written text (image descriptions) that a hostile publisher could craft to look like instructions. Those results, along with container details, user lists, audit entries and network paths, are fenced as untrusted data that Tainy is told never to follow, and text inside them cannot close the fence early. Once external content is in a conversation, every later approval card carries a provenance warning so you check the action is the one you asked for. As before, nothing that changes state runs without your approval.
- **Tainy checks tool input like the UI does.** Cluster firewall rule fields and the bridge, storage and volume ids used to create containers and VMs are validated the same way the UI forms validate them.
- **Tainy permission checks match the pages they mirror.** The cluster firewall rule tools need Manage settings and Manage security on the site, heartbeat status is admin only, setting a site location needs Manage sites and access to the site, and taking a config snapshot needs Manage settings on the site.
- **Tainy has burst and size limits.** The daily token and tool-call budgets limited total spend but not speed, so a user or a stolen session could burn a day's budget against the site API key in seconds. Messages are now capped at 10 per user per minute on top of the daily budgets, and hitting the limit is audited. A turn also stops after a fixed number of model rounds or when the budget runs out, oversized requests are refused and saved chats are capped in size.
- **Data stores fail loudly instead of resetting.** If the user store cannot be read, Tainer shows an error instead of treating it as empty and reopening first-run setup, and an unreadable `api-tokens.json` no longer silently drops every API token. New data files and folders are readable only by the Tainer user.
- **Stray WebSocket connections are closed.** Upgrade requests to unknown paths get an error response and are disconnected instead of being held open.
- **Onsite deploy script hardened.** `scripts/deploy-onsite.sh` no longer has a built-in host or password, checks SSH host keys, keeps the sudo password off the remote command line and stops exposing plain HTTP on port 3000 next to the HTTPS proxy. Set VM_HOST (and optionally DEPLOY_PASSWORD and TAINER_HOSTNAME), and connect with ssh once first to verify the fingerprint.
- **Dependency security updates.** Next.js, ws, nodemailer, maplibre-gl and js-cookie are updated to versions that fix known advisories, including a Server Action SSRF and several denial of service issues in Next.js. Unused packages no longer ship in the image, and the server bundler is pinned instead of downloaded at build time.

## [1.5.0] - 2026-07-09

### Added

- **Configurable agent ingest URL.** The LLDP/SNMP setup snippet previously hard-baked Tainer's public origin (`APP_URL`) as the address agents POST to — which fails on LAN deployments where Proxmox nodes can't resolve that hostname (the agent dies with `curl: (6) Could not resolve host`). There's now a per-site **Agent ingest URL** override in Network → Integrations (admin / `manage-security`), plus a global `TAINER_AGENT_BASE_URL` env var. Precedence: per-site override → env var → request origin. The panel shows the effective URL currently baked into new snippets and its source. Validated as a bare origin (scheme + host + optional port, no path). Changing it only affects newly generated snippets; existing nodes keep their value until a token is re-issued or `/etc/tainer-lldp.env` is edited.
- **SNMP polling for the full switch front panel.** LLDP only ever shows the one port a Proxmox node plugs into — a 48-port switch rendered as a lonely single chip. Now, when an admin sets a per-site SNMP community string in **Network → Integrations**, each node's agent also polls every LLDP-discovered neighbour's management IP via SNMPv2c (`IF-MIB` walk: `ifDescr`, `ifAlias`, `ifOperStatus`, `ifAdminStatus`, `ifSpeed`/`ifHighSpeed`, `ifType`, `ifMtu`) on a configurable timer (default 5 min) and POSTs the inventory to a new `/api/internal/snmp-ingest` endpoint. The device detail page then renders the **real chassis** — every physical port with true up/down/admin-disabled state, port names, operator aliases, and link speed, in a UniFi-style front panel with per-port LEDs; LLDP-observed ports get a sky-blue ring so you can see at a glance where your nodes terminate. Falls back to the LLDP-inferred mock when SNMP isn't configured. The community string is stored AES-256-GCM-encrypted under `AUTH_SECRET` (same as 2FA/OIDC secrets), never echoed back to the UI, and only baked into the agent setup snippet at token-issuance time. Same trust model as LLDP — the agent reaches *out*; Tainer never connects in. The extended setup snippet installs `snmp`+`jq`, ships a `tainer-snmp-poll.sh` script, and wires a `tainer-snmp.timer`; it no-ops cleanly until a community string is set, so you can enable SNMP later without re-running it on every node.
- **Tainer Copilot — an embedded AI assistant for diagnosing and managing your cluster** (sidebar slides out from the right, `Cmd/Ctrl+J` to toggle; new "Copilot" entry in the main nav). Ask questions like "what's running on prod?", "which container is using the most memory?", or "restart container 101"; the assistant calls a curated catalog of Tainer/Proxmox tools (list_sites, list_containers, get_container, list_storage_pools, start/stop/restart/shutdown_deployment, update_deployment_resources, destroy_deployment, get_audit_log, etc.) to answer or act. New containers can be launched with a **static IP from a pool** too ("deploy grafana with a static IP from the server pool") — the create tool takes an IP pool and assigns the first free address (or one you name) instead of DHCP. It can **delete many at once** too: "delete ignition-02 through ignition-10" is a single `destroy_batch_deployments` call — one confirmation for the whole set, and running guests are hard-stopped first automatically (in parallel, with a bounded wait so a stuck stop can't hang the turn) instead of the old one-at-a-time stop-then-delete dance that stalled on slow models. And it can **create many at once**: "create 10 from the grafana template with static IPs from the server pool" plans all ten hostnames and addresses, shows the full hostname→IP table on a single approval card, and creates the whole batch after **one** confirmation (each container gets its own one-time root password). The first N free pool addresses are reserved in order; if the pool doesn't have enough, it says so rather than half-creating. The copilot's tool catalog also grew a **Backups** group (list all/per-deployment, create a no-downtime backup, restore over a stopped guest with a typed-name confirm), **historical metrics** (`get_deployment_metrics` — CPU/memory/network avg + peak trend over hour→year, rendered as sparklines), **node migration** (move an LXC/VM to another node), and **tag management** (list a site's tags with member counts, add/remove tags on a guest). Rounding it out: **firewall** management (list cluster rules, add a rule, delete by position with a typed confirm), **VM template** listing (creation stays in the UI where ISO/cloud-init choices live), and a set of **admin/config reads** — backup & alert policies, node config snapshots (plus capture-a-snapshot), the ISO library, and read-only user/group listings ("who doesn't have 2FA?", "which group grants admin?"). Deliberately kept out of the copilot: node-config *restore*, user/group *mutations*, and any shell/outbound action — those stay UI-driven to preserve the assistant's no-exfiltration, least-privilege boundary. All go through the same permission/approval model as the rest. And it can **navigate for you**: "take me to that container" opens the deployment's detail page directly (internal app paths only — the assistant cannot send your browser to external URLs). The sidebar is **page-aware**: on a deployment detail page a context chip (e.g. "CT 101 · pve1") shows that "this container" questions resolve to that deployment — click it to detach the context and ask about anything else. **Conversations persist**: every chat auto-saves after each reply (per-user, newest 20 kept, approval tokens stripped) and the history panel in the sidebar header reopens or deletes previous chats — tool cards and all. **Permissions are inherited from your Tainer session** — every tool call goes through the same `requireSession` / `requirePermission` / `requireSiteAccess` / per-site checks the UI uses, so the copilot can never see or do anything you can't. Read tools (list, get, metrics) auto-run; write tools (lifecycle, resource updates) require a one-click approval card in the sidebar with a diff-style summary; destructive tools (delete) additionally require typing the deployment name to confirm. Approval is enforced by a server-issued AES-256-GCM-encrypted token (5-minute TTL, bound to the user's id) — the model can plan whatever it wants, but nothing executes without a fresh token from the approve button. ### Fixed

- **IP pool subnet parsing was broken for any network with first octet ≥ 128.** A 32-bit signed-int overflow in `parseSubnet()`: `addressInt & mask` returns a signed integer, so for `192.168.x`, `172.16.x`, or any public range the computed `networkInt`/`firstHostInt`/`lastHostInt` flipped negative. Range comparisons in `validateGateway` then rejected legitimate gateways like `192.168.100.1` for `192.168.100.0/24` with "Gateway must fall within the selected subnet's usable host range" — even though it is. The string outputs were correct (`intToIpv4` uses `>>>` which is unsigned), masking the bug for years. `10.x.x.x` happens to have the high bit clear so worked fine. Added explicit `>>> 0` coercion to `networkInt` and `broadcastInt` to keep them in unsigned space throughout.
- **Server actions that did `return withSiteConfig(...)` (no `await`) bypassed their own try/catch when the inner work threw.** In an async function, `return rejectedPromise` propagates the rejection to the awaiter without triggering the surrounding `catch` — so when a form submission threw (e.g. invalid IP pool gateway, bad subnet, malformed input), the rejection escaped the action and Next.js surfaced "Application error: a server-side exception has occurred" instead of the intended error toast. 61 call sites across 18 `*-actions.ts` files were patched to `return await withSiteConfig(...)`. Operators now see the specific validation error inline, as originally designed.
- Audit-log writes are now serialised through the same single-writer mutator queue used by the auth and IdP stores. The previous read-modify-write pattern could lose entries when two admin actions completed at the same instant — exactly the moment when a clean trail is most useful.
- Identity-provider create / update / delete actions now call `revalidatePath("/identity-providers")` instead of the non-existent `/settings/identity-providers`, so the providers list stops showing stale state after admin changes.

### Security

- **Rate-limit bypass via `X-Forwarded-For` header (RL-1).** The login and password-reset rate limits keyed on `email:ip`, where the `ip` was read straight from the `X-Forwarded-For` request header. A direct caller could rotate the header per request to mint a fresh bucket and effectively defeat per-IP lockout. `X-Forwarded-For` is now ignored unless `TAINER_TRUST_PROXY_HEADERS=true` is set explicitly; the default falls back to per-email rate limiting, which the attacker cannot rotate around.
- **Cross-site information disclosure on `/api/proxmox/rrd`, `/api/proxmox/task-status`, `/api/sites/overview`, and `/api/sites/status` (AUTHZ-1).** These routes only checked that the caller had a session, not that they had access to the requested site. Any logged-in operator could pull RRD time-series, poll task UPIDs, and enumerate every enabled site (status, location, deployment count, version banner) — including sites their permissions didn't cover. Each route now enforces `hasSiteAccess` per-request or filters the response to `accessibleSiteIds`.
- **SSO email-match account takeover (SSO-1 / C1).** When an OIDC sign-in didn't match an existing IdP-linked record, `signInWithSso` fell back to matching by email and silently bound the SSO subject to whatever local user owned that address. An attacker who could register a target's email at a permissive IdP could sign in as that local user — including admins. Email-fallback now refuses to adopt accounts that have a local password, 2FA enrolled, or a different SSO link; an admin must explicitly link the provider first. The `email_verified` claim is also enforced — sign-in is refused outright when the IdP reports the email as unverified.
- **2FA bypass via SSO (SSO-2 / C2).** The previous SSO path issued a session for any matched user without checking 2FA, so an SSO-eligible identity at the IdP bypassed local TOTP entirely. Combined with the email-match guard above, users with 2FA enrolled can no longer be adopted by a fresh SSO sign-in — the account stays under local-credential control until an admin links it.
- **OIDC issuer accepted `http://` (OIDC-1 / H1).** Issuer validation accepted any `http://` or `https://` URL, leaving discovery and token exchange MITM-able when an admin pasted a non-HTTPS issuer. `http://` is now rejected unless `TAINER_OIDC_ALLOW_INSECURE_ISSUER=true` is set explicitly for local development.
- **Auto-provisioning admins with no domain restriction (CFG-1 / M1).** The IdP-provider validator allowed `autoProvision: true` together with `defaultRole: admin` and an empty `allowedEmailDomains` — a foot-gun that turned anyone who could sign in at the IdP into a Tainer admin. The validator now refuses that combination and asks for an explicit allow-list.
- **Email-domain allowlist misclassified multi-`@` addresses (M5).** `isEmailAllowed` used `split("@")[1]`, so an address like `attacker@evil.example@trusted.example` matched as `evil.example` and could pass an allowlist that only named `trusted.example`. The check now uses the substring after the *last* `@`, matching canonical mailbox parsing.
- **Password-reset links no longer persisted to disk (DBG-1).** When SMTP was unconfigured, password-reset URLs (containing the single-use reset token in the path) were written to `password-reset-debug.json` in the data directory and kept for the last 25 attempts. Any disk-level read — backup leak, snapshot copy, post-RCE — let an attacker hijack pending resets. The link is now logged to stderr only; the operator running the container reads it from container logs and it disappears with the line.
- **Cluster credentials no longer logged on every RRD request.** The `/api/proxmox/rrd` handler logged the active site's `apiUrl` and `username` per request, exposing them to anyone with read access to container logs. Both log lines were removed.
- **Source maps no longer ship in the production Docker image (F1/F10).** The Dockerfile previously deleted `*.map` files in a `RUN` step *after* the `COPY --from=builder /app/.next` — but Docker layers are append-only, so the original bytes still lived in the COPY layer and were extractable from any pulled image via `docker save | tar -x`. Cleanup is now done in the same `RUN` as `npm run build` in the builder stage, so the runtime stage never sees source maps in its history. (Existing published images should be re-pulled / re-built to benefit; the old layers remain on Docker Hub.)
- **`AUTH_SECRET` is now mandatory in production (F6).** The auth secret is the crypto root for session cookies, mobile JWTs, 2FA secrets, and Proxmox credential encryption. Tainer used to auto-generate one to `auth-secret.txt` in the data directory if `AUTH_SECRET` was unset — convenient, but it meant any disk-level read (backup, snapshot, post-RCE) handed an attacker the ability to mint admin sessions and decrypt every Proxmox password. When `NODE_ENV=production` the app now refuses to start without `AUTH_SECRET` set as an env var, and the error message tells you to generate one with `openssl rand -base64 32`. The on-disk fallback is still available for development.
- **`manage-groups` privilege escalation to admin (RBAC-1 / C3).** A user with the `manage-groups` permission — intended for shuffling membership of non-privileged groups — could create a new group with `isAdmin: true` and assign themselves to it. `updateUserGroups` derives `user.role` from group membership, so the assignment flipped the caller to admin and the admin-role short-circuit in `hasPermission` then granted full takeover. Operations that touch admin groups (creating one, flipping `isAdmin` on or off, assigning a user into one) now require admin role explicitly, and self-promotion via the group-assignment endpoint is blocked outright as a defense-in-depth guard.

### Removed

- **The `role === "admin"` short-circuit in capability checks.** Previously `hasPermission(session, p)` returned `true` for any `p` whenever `session.user.role === "admin"` — any code path that flipped role to admin granted everything regardless of what `permissions` actually contained. Admins now have the full permission set populated explicitly in `session.user.permissions` at session-hydration time, and `hasPermission` is strict list-membership. Visible behaviour is unchanged (admins still do everything), but a future regression that mutates role outside the group-management path can no longer escalate. `requireAdminSession` and the binary "is admin?" UI checks (sidebar visibility, page-level admin-only gates) keep using `role` as before — only ad-hoc capability gates were affected.

### Changed (security)

- **Container `/app` is no longer writable by the runtime user (IMG-1).** The Dockerfile now `chown root:tainer /app` with `0750`/`0640` perms; only `/app/data` is writable by `tainer`. A future code-exec-in-container bug can no longer rewrite `server.mjs`, `node_modules/`, or `.next/server/*.js` for persistence across restarts.

- **Sign-in methods card on /account.** Shows whether your local password is active and which SSO provider you're linked to. After linking SSO (any sign-in via the SSO button on /login does this automatically — it matches by email if a stable IdP `sub` hasn't been seen yet), a "Disable local password" panel appears with a typed confirmation. Disabling clears the scrypt hash, revokes every other active session, and commits the account to SSO-only sign-in. The password reset email still works as a recovery path if SSO ever breaks.
- **SSO via OpenID Connect.** Configure identity providers (Microsoft Entra ID, Google Workspace, Okta, Keycloak, Auth0, GitHub Enterprise — anything that speaks OIDC) at `/identity-providers` (admin-only). Each provider gets a "Sign in with {name}" button on the login page. PKCE + state + nonce + ID-token signature validation are all enforced. Client secrets are encrypted at rest with the same AES-256-GCM helpers used for 2FA secrets. Per-provider settings include allowed email-domain list, default role for auto-provisioned users, and an enable/disable toggle. SSO users skip Tainer's TOTP 2FA — the IdP enforces that upstream. Audit log records every SSO sign-in distinctly from password logins, including newly-provisioned users. SAML support is intentionally deferred until someone asks.
- **Release tooling.** `scripts/release.sh` cuts a tagged release: refuses on a dirty tree, shows commits since the last tag, lets you confirm `[Unreleased]` coverage, atomically renames `[Unreleased]` → `[X.Y.Z] - YYYY-MM-DD`, opens a fresh `[Unreleased]`, commits, and tags `vX.Y.Z`. `scripts/changelog-status.sh` is a read-only audit helper that lists what has accumulated since the last tag.
- **Coverage check in `scripts/changelog-status.sh`.** Each commit since the last tag is now marked ✓ green (touched `CHANGELOG.md`), ✗ red (touched `src/` but missed `CHANGELOG.md`), or · gray (internal-only), with a summary line and a colourised view of the current `[Unreleased]` block. Honours `NO_COLOR` and disables colour automatically when stdout is not a TTY.
- **Node config restore.** Snapshots can now be applied back to Proxmox via a new restore page with side-by-side diff against live config, per-section selection (network, DNS, hosts, timezone, storage, firewall), opt-in destructive mode for cluster-wide sections, and a typed `RESTORE` confirmation gate.
- **Node config snapshot view page.** Read-only browser for snapshot contents, reachable via the eye icon on each snapshot row.
- **Scheduled node config snapshots.** Per-site interval-based schedules (1h / 6h / 12h / 24h / 48h / weekly) with per-policy retention, pause / resume, run-now, and delete. Manual snapshots are unaffected by per-policy retention.

### Changed

- **Hung Proxmox endpoints no longer drag down the whole app.** Three related fixes that compound: (1) every Proxmox request now has a hard 15-second timeout — without this, a flaky RRD endpoint or a slow node could hold a keep-alive socket indefinitely and queue up subsequent requests behind it. (2) The load balancer's per-site timeout dropped from 30s to 10s, and its site iteration is now parallel instead of sequential — previously a single unresponsive site blocked every other site's tick for up to 30 seconds. (3) The keep-alive `maxSockets` limit went from 16 to 32 so background ticks (load balancer, alerts) can't starve user-facing pages. Together: a misbehaving site fails its own queries quickly without leaking stalls into healthy sites.
- **Massive speedup on the deployments page (and every other Proxmox-heavy page).** Three problems were stacking on top of each other: (1) every Proxmox call was opening a fresh TCP+TLS connection because there was no `https.Agent` with `keepAlive`, costing 50–150ms per request × 90+ requests on the deployments page; (2) for every running container the page was making a slow `/lxc/{vmid}/interfaces` call (1–2s each) just to fetch the IP, even when the IP was already statically configured in `net0`; (3) the deployments page declared both `force-dynamic` and `unstable_cache`, so the cache was silently disabled (this one slipped through Phase 1 of the perf pass). Fixed all three. Expected improvement: 10s → ~1–2s for the typical deployments load, with most of that being the first uncached fetch.
- **Faster page loads across the app.** Bumped Proxmox GET cache TTL from 1.5s → 10s and JSON file cache TTL from 1s → 5s — the previous values were too short for cascading reads inside a single page render to share data, so even pages that "should" be cached were re-fetching from Proxmox / disk on every related call. Both caches still invalidate on writes, so freshness is unaffected.
- **`unstable_cache` actually works now.** Removed `export const dynamic = "force-dynamic"` from seven pages that also use `unstable_cache` (dashboard, settings, images, tags, tag detail, ISO images, templates). The `force-dynamic` directive was silently disabling the cache, turning every request into a full Proxmox refetch. The cache's `revalidate` (5–30s depending on page) is now in effect, eliminating duplicate Proxmox calls within the cache window.
- **Background scheduler is faster.** The four scheduler checks (alerts, backups, config snapshots, heartbeat) now run in parallel via `Promise.all` instead of sequentially, and the per-site config-snapshot iteration uses bounded concurrency (3 sites at a time) instead of one-at-a-time. Expected savings: 100–300ms per 30-second tick.
- **`getTemplateIndex()` parallelism.** The `listAvailableTemplates` Proxmox call previously waited for the entire first batch of three calls before starting. It now chains off just `listTemplateTargets` via `.then()` and runs in parallel with the other two, so the slowest single call dominates instead of the chain.
- **`TaskToastProvider` no longer churns the context every poll.** The `activeTaskUpids` Set is now reference-stable: it returns the same Set when content is unchanged, so consumers (deployment cards, snapshot cards, etc.) only re-render when a task actually starts or finishes — not every 2-second progress update.
- **Shared scheduler helpers.** `computeNextRunAt()` and the "find due policies, run, mark, capture errors" loop now live in `src/lib/scheduler-utils.ts`. Backup and config-snapshot engines use the shared helper; engine-specific complexity stays per-engine.
- **`NodeConfigSnapshot` type** gained optional `policyId` and `trigger` fields so scheduled snapshots can be attributed and per-policy retention can prune only the right ones. Legacy snapshots without these fields default to `trigger: "manual"`.

### Fixed

- 500 on `/sites/[siteSlug]/node-configs` caused by exporting non-async values from a `"use server"` file. Restore action state moved to a companion `node-config-action-states.ts` file.
- **SSO sign-in landing on /login until reload.** The session cookie was set with `sameSite: "strict"`, so when the browser followed the cross-site redirect chain back from the IdP (Microsoft → Tainer callback → `/`) it refused to send the cookie on the first navigation. Reloading worked because that second navigation is unambiguously same-site. Switched to `sameSite: "lax"` for the session cookie — still blocks CSRF on cross-site form POSTs (the threat strict actually defends against), just allows top-level navigations from external sites which is exactly what an OIDC callback is.
- **OIDC callback failing with `"currentUrl" must be an instance of URL, or Request` and bouncing to `https://0.0.0.0:3000/login`.** Two stacked bugs in the SSO callback: (1) `request.nextUrl` was passed to openid-client v6 — a `NextURL` instance which can fail openid-client's `instanceof URL` check across module boundaries when Next.js bundles its URL global separately. Now we construct a plain `new URL(...)` and pass that. (2) Inside Docker, `request.url` and `request.nextUrl.origin` can be the bind socket (`http://0.0.0.0:3000`) instead of the public URL, so any `new URL("/login", request.url)` redirect lands at a broken address. A new shared `getPublicOrigin()` helper resolves the canonical public URL from `APP_URL` env var (set by the deploy script) → `x-forwarded-*` headers → request URL, in that order, and is used by both the initiate and callback routes so the redirect_uri sent to the IdP matches exactly what the callback expects.

### Removed

- Dead code: `src/components/live-refresh.tsx` and `src/components/auto-refresh.tsx` — neither was imported anywhere. The audit had flagged a 15-second `router.refresh()` interval as a perf issue; it doesn't exist on any active page.
- **False "Will change" diffs in node config restore preview.** Proxmox returned the same DNS object with keys in different orders on different reads, and the diff did string equality on `JSON.stringify`, so identical-but-reordered objects were flagged as changed. JSON formatting now recursively sorts object keys, sorts arrays of objects by their stable identity field (`iface`, `storage`, `pos`), and canonicalises Proxmox set-valued comma-string fields (`content`, `nodes`, `tags`) by splitting + alphabetising. Semantically-equal sections show "No change" regardless of the order Proxmox returned them in.
